SimAI Architecture

Full-Stack Distributed AI Training & Inference Simulator
Alibaba Cloud · NSDI’25 · aliyun/SimAI

Overview

SimAI is a full-stack, high-precision simulator for large-scale LLM training and inference. It models the entire distributed AI stack: from training framework orchestration and computation kernels, through collective communication library behavior, down to packet-level network transport.

The motivation is pragmatic: GPU clusters cost millions to procure, and most capacity runs production workloads. Before deploying a new network topology, parallelism strategy, or hardware generation, teams need to evaluate performance via simulation. SimAI achieves 98.1% average alignment with real-world training results across diverse scenarios.

Five Components SimAI is composed of five independently-developed subsystems wired together: AICB workload generation → astra-sim framework simulation → SimCCL collective decomposition → ns-3 network simulation → Vidur inference scheduling.

1. AICB — AI Communication Benchmark

AICB (aliyun/aicb) is SimAI’s workload generation layer. Unlike generic network benchmarks (nccl-tests, perftest), AICB generates communication workloads with precise patterns aligned to actual model training: the exact sequence, type, and data size of every collective operation that occurs during a training iteration.

AIOB — AI Operation Benchmark

AIOB is embedded within AICB and profiles computation kernels on target GPUs to obtain real execution times. SimAI supports three computation time sources:

  1. AIOB profiling — run kernels on target GPU, measure wallclock
  2. Parameter extrapolation — TXPU = α × TA100 where α = f(kernel_type, FLOPS_ratio, BW_ratio)
  3. GPU simulator — GPGPU-Sim for unknown hardware microarchitectures

Astra-sim originated at Georgia Tech / Meta / Intel (ISPASS 2020, 2023). SimAI extends the 1.0 branch (astra-sim/astra-sim/tree/ASTRA-sim-1.0) with substantial modifications including MockNccl integration, fast-backend acceleration, and RDMA physical network support.

3. SimCCL — Collective Communication Library Simulator

SimCCL (aliyun/SimCCL) decomposes high-level collective operations into sets of point-to-point (P2P) Send/Recv operations, faithfully reproducing NCCL’s behavior without requiring GPUs. Only 572 lines from the NCCL codebase are essential — algorithm selection, chunking, and channel assignment logic.

Algorithms & Protocols

Figure 6 — NCCL algorithm × protocol matrix modeled by SimCCL. Each cell has hardware-specific latency/bandwidth constants.

P2P Decomposition Flow

The core decomposition happens in MockNcclGroup::genFlowModels(). It takes a collective specification and produces a map of SingleFlow objects — each representing one P2P transfer with explicit dependencies: 

struct SingleFlow {
  int flow_id;                    // Unique flow identifier
  int src, dest;                  // Source and destination ranks
  uint64_t flow_size;             // Data size for this flow
  vector<int> parent_flow_id;     // Flows that must complete first
  vector<int> child_flow_id;      // Flows dependent on this one
  int channel_id;                 // Which channel (for multi-channel)
  int chunk_id;                   // Which chunk (for pipelining)
  string conn_type;               // "RING", "PXN_INIT", etc.
};

Bus Bandwidth Calculation

calbusbw.cc computes effective bus bandwidth for each algorithm, factoring in hardware topology:

GPUNVLink BWPCIe BWNIC BWNVLS BW
H10018 × 20.6 = 370.8 GB/s51.2 GB/s (Gen5)48.5 GB/s (CX-7)475.0 GB/s
H8008 × 20.6 = 164.8 GB/s51.2 GB/s48.5 GB/s215.0 GB/s
A10012 × 20.0 = 240.0 GB/s25.6 GB/s (Gen4)23.5 GB/s (CX-6)—

The effective bus bandwidth is computed as:

Ring:  busbw = min(nvlink_bw, nic_bw × nics_per_node) × (N-1)/N
Tree:  busbw = min(nvlink_bw/2, nic_bw × nics) × (N-1)/N  [with correction factors]
NVLS:  busbw = nvls_bw × gpus / (gpus-1)                      [H100/H800 only]
Best:  max(ring, tree, nvls)

5. Vidur — Inference Simulation

Vidur (originally from Microsoft Research, MLSys 2024) is an LLM inference simulator. Alibaba’s fork (vidur-alibabacloud) adds SimAI-backed communication time prediction, prefill/decode disaggregation (inspired by Splitwise), and MoE model support.

Event-Driven Simulation Loop

The Simulator class uses a min-heap priority queue. Events are processed in time order:

Figure 10 — Vidur’s event-driven inference simulation. Each batch stage queries the ExecutionTimePredictor, which can invoke SimAI as a subprocess.

Prefill/Decode Disaggregation

Inspired by the Splitwise approach, Alibaba’s Vidur fork supports disaggregated prefill and decode pools. Prefill-heavy requests run on dedicated nodes; after prefill completes, the KV cache is transferred to a decode node via point-to-point communication:

Figure 11 — Disaggregated serving: separate compute-optimized prefill pool and memory-optimized decode pool with KV cache transfer.

SimAI Integration

The key integration is in sklearn_execution_time_predictor.py. The TPTimePredictor class generates AICB workload files (SimAIWorkload) and invokes the SimAI binary as a subprocess:

  1. Vidur creates a SimAIWorkload with model dimensions and batch parameters
  2. Workload is written to a temp file; a content hash caches results
  3. SimAI binary (SimAI_analytical or SimAI_simulator) is spawned
  4. CSV output is parsed back into execution time estimates
  5. Results feed into Vidur’s event-driven scheduler

Supported backends: aicb (direct AICB call), simai_analytical (busbw-based), simai_simulation (full ns-3 packet simulation).

Training Simulation (Model-Agnostic)

The training side (AICB + astra-sim) is not tied to specific model names. It takes raw parameters: 

hidden_size, num_layers, num_attention_heads, intermediate_size,
num_experts, num_experts_per_tok, sequence_length, micro_batch_size

Any transformer architecture works — you supply the dimensions and parallelism config, AICB generates the workload. The workload file format encodes layer-by-layer compute times and collective operations, not model names. AICB profiles or extrapolates compute times for whichever GPU type you target.

Inference Simulation Deep Dive

This section traces exactly how a model config turns into per-request latency predictions. Understanding this path is essential for interpreting Vidur’s output and extending it to new models.

Execution Time Predictor

The SklearnExecutionTimePredictor is initialized once at startup. Its __init__:

  1. Loads 5 profiling CSV files (compute, attention, CPU overhead, AllReduce, SendRecv)
  2. Filters each CSV by exact match on model architecture dimensions
  3. Trains lightweight sklearn models (RandomForest with GridSearchCV, MAPE scorer)
  4. Pre-computes all possible predictions into Python dicts for O(1) lookup at runtime
Critical design point: Architecture parameters (embedding_dim, num_heads, etc.) are used as filters to select the right profiling dataset, NOT as ML features. A different model architecture requires a separate profiling run and separate CSV files. The actual ML features are deliberately minimal: num_tokens, batch_size, kv_cache_size.

Profiling CSV Filtering

Each profiling CSV is filtered by exact equality on model config fields:

df[
    (df["n_head"]   == model_config.num_q_heads)     &
    (df["n_kv_head"] == model_config.num_kv_heads)   &
    (df["n_embd"]    == model_config.embedding_dim)   &
    (df["n_expanded_embd"] == model_config.mlp_hidden_dim) &
    (df["use_gated_mlp"]   == model_config.use_gated_mlp)  &
    (df["vocab_size"]      == model_config.vocab_size)      &
    (df["num_tensor_parallel_workers"] == tensor_parallel_size)
]

num_tokens_rounded is (total_tokens + 7) // 8 * 8 — the total tokens across all requests in the micro-batch (both prefill and decode tokens combined), aligned to 8 for CUDA kernel efficiency. This single feature drives most linear-layer predictions.

Attention: Prefill vs Decode

Attention gets separate models because the compute profiles are fundamentally different:

  • Prefill: O(n²) flash-attention. Features: (kv_cache_size, prefill_chunk_size²) — the quadratic term captures the self-attention complexity
  • Decode: O(n) per-token attention. Features: (batch_size, avg_kv_cache_size) — linear in both dimensions

KV cache size is quantized to nearest multiple of 64 (matching paged KV block size) for lookup efficiency.

SimAI Subprocess Protocol

When using the simai_analytical or simai_simulation backend:

  1. Compute AllReduce tensor size: bytes = hidden_size × num_tokens × dtype_bytes
  2. Write a SimAIWorkload file with one layer: forward_comm=ALLREDUCE, forward_comm_size=bytes
  3. Compute an MD5 hash of the workload content for caching
  4. Spawn the SimAI binary as a subprocess with topology/config args
  5. Parse the output CSV (last row, column for end-to-end time in μs)
  6. Convert μs → ms, add NCCL CPU launch overhead
  7. Cache result by (hidden_size, num_tokens, dtype_bytes)

Time Aggregation: From Components to Total

The ExecutionTime class assembles per-kernel predictions into total batch execution time. The key insight: AllReduce is counted twice per transformer block — once after attention and once after MLP, matching the two AllReduce collectives in standard tensor parallelism. 

attention_block_time =
    attn_pre_proj + attn_post_proj + attn_prefill + attn_decode
    + attn_kv_cache_save + attn_rope(=0) + input_layernorm
    + tensor_parallel_allreduce                                    ← 1st AllReduce

mlp_block_time =
    mlp_up_proj + mlp_down_proj + mlp_act
    + post_attention_layernorm
    + tensor_parallel_allreduce                                    ← 2nd AllReduce

transformer_block_time = attention_block_time + mlp_block_time + residual_add

model_time = (transformer_block_time × layers_per_PP_stage
              + pipeline_parallel_send_recv) × 1e-3              ← ms → seconds

total_time = model_time + cpu_overhead × 1e-3
Per-layer MoE path (AICB backend): For MoE models (DeepSeek-671B, Qwen3-MoE), the predictor iterates layer-by-layer and reads pre-computed AICB CSV data instead of using the sklearn models. MoE communication time is computed as comm_size / bandwidth where bandwidth is either rdma_bandwidth (inter-node EP) or nvlink_bandwidth (intra-node EP), hardcoded in the replica config.

Kernel Simulation: What SimAI Does and Does Not Model

A common misconception: SimAI does not simulate GPU kernels. It never models what happens inside a CUDA/HIP kernel — no register allocation, no warp scheduling, no memory coalescing. Every kernel is treated as a black-box timing number.

Method 1: AIOB Profiling (Primary)

Run the actual kernel on the target GPU, measure wallclock time, record to CSV:

Figure 15 — Kernel timing pipeline: real GPU profiling → CSV → sklearn curve fit → O(1) dict lookup at simulation time.

Method 2: Parameter Extrapolation (For Unavailable GPUs)

When the target GPU is not available for profiling, SimAI extrapolates from a reference GPU (typically A100): 

TimeTargetGPU = α × TimeA100

α = f(kernel_type, FLOPStarget/FLOPSA100, MemBWtarget/MemBWA100)

The scaling factor α depends on whether the kernel is compute-bound (scale by FLOPS ratio) or memory-bound (scale by bandwidth ratio). This is essentially a roofline-model extrapolation.

Method 3: GPU Microarch Simulator (Rare)

For truly unknown hardware (pre-silicon evaluation), the paper mentions using GPGPU-Sim for microarchitectural simulation. This is outside SimAI itself and used only as a last-resort source for kernel timing numbers.

The Simulation Boundary

This table clarifies exactly what SimAI simulates versus what it treats as empirical input:

AspectSimulated?Method
Kernel compute time (matmul, attention, norm, etc.) No Profiled on real GPU or extrapolated
NCCL algorithm selection (Ring/Tree/NVLS) Yes MockNccl reimplements NCCL’s selection heuristics
Collective → P2P decomposition Yes SimCCL generates SingleFlow DAGs with channel pipelining
Network packet transport Yes ns-3 models RDMA, congestion, PFC, ECMP packet-by-packet
Compute-communication overlap Yes Astra-sim event engine schedules WG comm overlapping next IG
Pipeline bubble Yes (PP-1)/(GA×VPP) formula from Layer.cc
Memory bus (NPU ↔ HBM) Yes LogGP model in MemBus.cc
Request scheduling & batching Yes Vidur event-driven scheduler (ORCA, vLLM, Sarathi, etc.)
KV cache management Yes Paged KV cache with block-level tracking
Warp scheduling / register allocation No Not modeled — abstracted by profiling
CUDA driver / runtime overhead No Absorbed into profiling measurements
Why this works: Kernel execution time is deterministic for a given (op, shape, dtype, GPU) — it does not change with network topology or parallelism strategy. Profiling once on real hardware gives ground truth. The interesting simulation happens in communication and scheduling, where collective algorithms, network congestion, and compute-comm overlap interact in non-obvious ways. That’s where SimAI’s 98.1% accuracy comes from: precise network simulation on top of empirical kernel timing.

Key Design Decisions

1. Selective High-Fidelity Integration Rather than simulating everything at the lowest level, SimAI integrates only the parts that matter for accuracy. Only 572 lines from NCCL’s codebase are essential — the algorithm selection, chunking, and channel assignment logic. GPU kernel code, driver interactions, and CUDA runtime are abstracted away.
2. Lock-Free Multi-Thread Acceleration SimAI uses std::atomic<bool> Sys::g_sys_inCriticalSection for lock-free global context sharing across threads. Each GPU rank runs in its own thread; the atomic flag serializes only critical sections. This achieves a 23× speedup over single-threaded execution.
3. Three-Mode Flexibility The same workload can be evaluated at three fidelity levels without modification. Analytical mode for rapid exploration (seconds), simulation mode for detailed analysis (minutes to hours), physical mode for ground-truth validation. Users iterate: analytical → simulation → physical.
4. Modular Composition over Monolith Each component (AICB, astra-sim, SimCCL, ns-3, Vidur) is a standalone project with its own repo, build system, and test suite. SimAI wires them together via well-defined interfaces: workload files (AICB → astra-sim), AstraNetworkAPI (astra-sim → ns-3), subprocess calls (Vidur → SimAI binary). This enables independent evolution and replacement.
5. Topology-Aware Communication SimCCL’s MockNcclGroup distinguishes NVLink (PATH_NVL), PCI (PATH_PIX/PXB), and network (PATH_NET) paths with hardware-specific latency/bandwidth tables. Algorithm selection automatically adapts to whether communication is intra-node or inter-node, matching real NCCL behavior.
6. PXN (Path-to-NIC) Optimization For multi-node ring collectives, SimCCL models NCCL’s PXN optimization: intra-node data is first gathered to the GPU closest to the NIC via NVLink, then sent across the network. This avoids PCIe/QPI bottlenecks and is critical for accurate inter-node bandwidth modeling.
7. Inference via Training Simulator Vidur reuses the training simulator for communication time prediction rather than building a separate comm model. This ensures inference TP communication estimates match training-validated accuracy. The integration is lightweight: subprocess call with cached results by content hash.
